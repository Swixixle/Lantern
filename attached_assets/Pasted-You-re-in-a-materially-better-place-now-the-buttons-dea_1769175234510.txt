P0 — Long extract durability: Web Worker is not enough by itself

If the user refreshes mid-extract, worker-based compute dies unless you have a durable job model. localStorage recovery of source text is helpful, but it is not durability of the extract.

Implement server-side job + polling now.
Web Worker may remain for “local mode,” but the primary path for long docs must be durable.

Required architecture (minimum viable)
	•	POST /api/extract → returns { job_id } immediately (no long request hangs)
	•	Server enqueues job (BullMQ/Redis, Cloudflare Queue, Postgres-backed queue—anything durable)
	•	GET /api/jobs/:job_id → returns:
	•	state: queued | parsing | extracting | sanitizing | scoring | packaging | complete | failed
	•	progress: 0–100 (coarse is fine)
	•	pack_id if complete
	•	error_code + recoverable_message if failed
	•	Client:
	•	stores job_id locally
	•	on refresh, reconnects to job_id and resumes polling
	•	if job is complete, pack appears in Library automatically

Non-negotiables:
	•	Source text never disappears during run.
	•	No indefinite spinner: add timeout thresholds per phase + a recoverable failure surface.
	•	Refresh mid-extract must either:
	•	reconnect and complete, or
	•	show explicit recoverable failure message (not silent death).
