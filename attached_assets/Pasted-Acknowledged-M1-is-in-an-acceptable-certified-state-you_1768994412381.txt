M2 directive: Do Persistence first, then Heuristics

Even though the original plan labels M2 as “Heuristic Reliability,” the correct sequencing for Lantern is:
	1.	Persistence (data durability + versioned schema + migration discipline)
	2.	Heuristic Reliability (because you need stable, real-world data to evaluate and regress heuristics)

Rationale: heuristic work without durable storage produces misleading results (you tune against ephemeral state and test fixtures). Persistence creates the substrate that makes heuristic improvements measurable, repeatable, and debuggable.

Call this M2: Persistence & Schema Evolution. Heuristics becomes M3.

⸻

M2 scope: Persistence & Schema Evolution (authoritative library state)

Goals (non-negotiable)
	•	Library survives refresh/browser restart.
	•	Library survives common failure modes (partial writes, schema changes).
	•	Import/export remains compatible via schema versioning + migrations.
	•	State is observable and testable (deterministic load/save behavior).

Storage choice

Use IndexedDB (via idb or Dexie) if packs can grow beyond trivial size or you anticipate binary assets / large receipts later. If you are certain packs remain small (a few hundred KB), localStorage is acceptable, but it is a trap long-term.

My directive: IndexedDB now. It prevents the “we have to migrate off localStorage” tax.

M2 deliverables (concrete)

1) Persistence Engine
	•	Create a small storage module:
	•	loadLibrary(): Promise<LibraryState>
	•	saveLibrary(next: LibraryState): Promise<void>
	•	clearLibrary(): Promise<void>
	•	Add write coalescing (debounce or “last write wins” queue) to avoid rapid successive writes.
	•	Add atomicity guard:
	•	Store as one record {schemaVersion, updatedAt, library} or a transactional multi-store write.
