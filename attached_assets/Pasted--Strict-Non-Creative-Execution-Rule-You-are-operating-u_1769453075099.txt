# Screen 4 — Conflict & Gaps (v1) Implementation Contract

## 1) Purpose (scope-locked)

This screen must answer only:

* **Where do sources conflict?**
* **Where is evidence missing for commonly attempted claims?**
* **Where is there a time-based mismatch (source predates/ postdates relevant reference points)?**

It must not:

* Resolve contradictions
* Suggest which side is “correct”
* Offer conclusions, rankings, or intent

Label is fixed:

**Screen title:** `Constraints & Friction`

---

## 2) Data model (minimum viable)

Create: `client/src/lib/schema/constraints.ts`

```ts
export type ConstraintType = "CONFLICT" | "MISSING_EVIDENCE" | "TIME_MISMATCH";

export interface ConstraintItem {
  id: string;                 // stable UUID
  type: ConstraintType;

  // Plain description of what the constraint is (no conclusions)
  summary: string;

  // Optional: the claim this constraint affects
  claim_id?: string | null;

  // References into evidence (anchors) when applicable
  anchor_ids: string[];       // may be empty for MISSING_EVIDENCE

  // Required when type = TIME_MISMATCH
  time_context?: {
    earlier_date?: string | null;   // ISO
    later_date?: string | null;     // ISO
    note: string;                  // e.g. "Primary source predates statutory update referenced in secondary source"
  } | null;

  // Required when type = MISSING_EVIDENCE
  missing?: {
    requested_assertion: string;    // e.g. "Ranking jurisdictions by strictness"
    reason: string;                // e.g. "No anchored comparative ranking exists in primary source"
  } | null;

  // Required when type = CONFLICT
  conflict?: {
    left: { anchor_id: string; source_document: string; page_ref: string };
    right:{ anchor_id: string; source_document: string; page_ref: string };
  } | null;
}
```

Hard requirements:

* `summary` must be descriptive, not interpretive.
* `anchor_ids` must be a union of any relevant anchors (including `conflict.left/right.anchor_id`).

## 3) API contract

### Endpoint

`GET /api/constraints?corpusId=<id>`

### Response

```json
{
  "corpus_id": "corpus-001",
  "constraints": [ /* ConstraintItem[] */ ]
}
```

You may mock initially, but the endpoint signature must exist.

---

## 4) UI requirements

### A) Entry point

Add a navigation element from Claim Space to:

`/constraints?corpusId=<id>`

(If corpusId is not yet real, pass a placeholder string consistently.)

### B) Layout

Render three sections in this order:

1. **Conflicts**
2. **Missing Evidence**
3. **Time Mismatches**

Each item must show:

* `summary`
* `type` label (small)
* Button: **View Evidence**

**View Evidence behavior**

* If `anchor_ids.length > 0` → route to Anchor View: `/anchors?ids=...`
* If `anchor_ids` empty → show neutral message inline:

  > “No anchors are available for this item in the current corpus.”

### C) Conflict item specifics

For `type = CONFLICT`, render two sub-panels:

* Left source (document + page_ref + anchor_id)
* Right source (document + page_ref + anchor_id)

Do not add any “which is stronger” or “likely correct” indicator.

### D) Missing Evidence item specifics

Render:

* `missing.requested_assertion`
* `missing.reason`

No remediation suggestions beyond what is in `reason`.

### E) Time mismatch specifics

Render:

* earlier_date, later_date (if present)
* `time_context.note` verbatim

No inferences like “therefore outdated”; only “predates/postdates” when explicitly encoded by the data.
