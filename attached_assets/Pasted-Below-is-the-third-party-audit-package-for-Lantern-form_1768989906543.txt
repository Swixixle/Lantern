2) Architecture overview (audit-style)
Type: Client-Side Single Page Application (React/Vite).
Context: "Mockup Mode" prototype. The backend folder exists but is explicitly bypassed for this version; all logic runs in the browser.

Observable Behavior: User pastes text -> Engine extracts structured data (Entities, Quotes, Metrics, Timeline) -> Results displayed -> User can save "Pack" snapshots locally -> Diff packs.
Core Module: lanternExtract.ts contains the deterministic extraction engine, hashing logic, and diffing algorithm.
Data Flow:
Input: User pastes raw text into Textarea.
Processing: extract() function (synchronous, client-side) parses text using regex heuristics.
Identity: computePackId() generates SHA256 hashes of content for deduplication.
Storage: localStorage (Key: lantern_packs).
External Services: None. No API calls are made. No LLMs are connected (simulated via heuristics).

4) Prompt handling report (no raw prompts)
Context: This version (v0.1.5) uses Regex Heuristics, not LLM Prompts. However, the logic serves the same purpose as a "System Prompt" in an LLM system.

Prompt Name: extract() function logic.
Intent: Identify structured knowledge in unstructured text.
Inputs: Raw string.
Outputs: JSON object with 4 lists (Entities, Quotes, Metrics, Timeline).
Constraints:
Entities must be capitalized.
Metrics must have known units (USD, EUR, %, etc.).
Quotes must be enclosed in double quotes.
Safety: Pure client-side code. No injection risk because "instructions" are hardcoded code, not natural language interpretation.

7) “Due diligence checklist” findings
What’s Solid
Engineering Rigor: The "Quality Contract" and regression testing harness are excellent. It self-validates determinism and provenance integrity.
Architecture: The separation of extract() (pure logic) from UI is clean.
Data Model: The LanternPack schema with content-addressed IDs (pack_id) prevents data duplication and enables robust diffing.
What’s Brittle
Extraction Logic: The regex heuristics are very basic placeholders. They will fail on real-world messy text (e.g., complex entities, non-standard quotes).
Persistence: localStorage is not a viable production storage solution.
Key Unknowns
LLM Integration: Phase 3 backlog mentions "Shadow NLP Engine" (Gemini/GPT). Integrating this while maintaining the "Provenance Integrity" constraint (strict character offsets) is a hard engineering challenge not yet solved here.
Top Risks
Heuristic limit: The current regex engine is too simple for production value.
Data Loss: Browser storage is ephemeral.
Performance: Large text inputs (>100k chars) processed synchronously in the main thread will freeze the UI.
Recommended Next Steps
Web Worker: Move extract() to a Web Worker to unblock the UI thread.
SQLite/IndexedDB: Replace localStorage with client-side SQL for robust storage.
LLM "Shadow" Mode: Implement the Phase 3 LLM integration to propose extractions that the heuristics miss.
Virtualization: Use react-window for rendering lists; the current list rendering will lag with >1000 items.
Export/Import: Add file-based Backup/Restore to prevent data loss.
